AGENTS.md — Fluxis EOD
Purpose
This file defines working rules for AI coding agents contributing to Fluxis, an Electronic Document Management System (EOD). Read docs/ARCHITECTURE.md before making architectural decisions. If that file is not present locally, follow the established repository conventions and the constraints below; do not invent missing requirements.
Project stack
- Frontend: Vue 3, Vite, TypeScript (strict), shadcn-vue, Tailwind CSS v4, Reka UI.
- Frontend libraries: Vue Router, Pinia, TanStack Query for Vue, TanStack Table for Vue, VeeValidate, Zod, Axios, Lucide (@lucide/vue), date-fns and Sonner (vue-sonner).
- Backend: Python, Flask (blueprints), REST/OpenAPI, SQLAlchemy with Flask-Migrate (Alembic).
- Data and OCR: SQLite by default (DATABASE_URI), OCR through Google Gemini (google-genai).
- Deployment: Docker Compose on a small Linux VPS, behind a reverse proxy.
- Architecture: modular monolith, feature-based frontend, separate background OCR worker.
- Do not add a second UI framework, a new backend framework, microservices, Kubernetes, or cloud-managed dependencies without explicit approval.
Before changing code
1. Inspect the repository, relevant modules, package manifests, and existing conventions.
2. Read docs/ARCHITECTURE.md, relevant README files, and DEFINITION_OF_DONE.md when present.
3. Identify the smallest change that satisfies the request. For larger work, outline a short plan before editing.
4. Reuse existing code and dependencies. Ask before introducing a major dependency, schema redesign, or breaking API change.
5. Do not assume an unfinished feature is implemented merely because a directory or interface exists.
Repository boundaries
- frontend/: Vue application and UI logic.
- backend/: Flask REST API and business logic (app/routes, app/services, app/models, app/schemas).
- backend/migrations/: Flask-Migrate (Alembic) database migrations.
- infrastructure/: container, proxy, and operational configuration.
- docs/: architecture and technical documentation.
- Respect the actual repository layout if it differs. Do not reorganize unrelated files as part of a feature.
Frontend rules
- Prefer Vue Single File Components with <script setup lang="ts"> and Composition API.
- Organize business functionality by feature; place shared primitives in components/ui/ and reusable app components in shared/common locations.
- Use shadcn-vue for UI primitives and Tailwind theme tokens for styling. Do not modify generated/vendor-like UI primitives for feature-specific behavior when a wrapper or composition suffices.
- Support responsive layouts, keyboard accessibility, semantic labels, focus states, and light/dark/system themes.
- Use TanStack Table for complex table behavior; handle loading, empty, error, and success states explicitly.
- Use VeeValidate and Zod for forms and client-side validation; server validation remains authoritative.
- Use TanStack Query for remote/server state, Pinia for genuinely shared client state, and local component state for local interactions. Avoid duplicating the same state across layers.
- Keep API requests in feature API modules or a shared typed client, not embedded throughout view components.
- Do not put secrets or authorization decisions in the frontend. Route guards improve UX but are not security boundaries.
Backend rules
- Keep Flask layers separate: blueprints in app/routes handle transport, app/services implement use cases, and app/models handle persistence.
- Validate incoming DTOs and configuration; use consistent API errors and appropriate HTTP status codes.
- Enforce authentication, permissions, and document access checks on the server for every relevant operation.
- Keep database changes in reviewed Flask-Migrate migrations. Never reset or drop a database, erase data, or apply destructive migrations without explicit approval.
- Generate and maintain OpenAPI documentation for changed endpoints; keep frontend contracts aligned.
- Record security-relevant actions in audit logs without logging credentials, tokens, or sensitive document content.
- Avoid synchronous OCR work inside HTTP request handlers. Process them in a background worker or job queue.
- Make background jobs retry-safe/idempotent where practical, with bounded retries, timeouts, and clear statuses.
Security and document handling
- Treat uploaded documents, OCR output, filenames, metadata, and external directory data as untrusted input.
- Validate file size, allowed formats, actual content type, and storage paths; prevent path traversal and unsafe file access.
- Store uploaded files in private storage, outside publicly served directories. Authorize download and preview endpoints.
- Never commit .env, private keys, credentials, real user data, or production documents. Maintain .env.example with placeholders.
- Use secure password hashing (Argon2id if local passwords are implemented) and safe session/token handling. Prefer HttpOnly and Secure cookies when applicable.
- Keep the database and any internal services on internal networks; do not expose them publicly in deployment examples.
- Use least-privilege settings and resource limits appropriate for a small VPS.
Git and scope control
- Work only on the requested task and directly necessary supporting changes.
- Do not overwrite or revert unrelated user changes, rewrite history, force-push, or create commits unless asked.
- Do not edit lockfiles manually. Use npm for JavaScript packages (frontend/package-lock.json) and pip with requirements.txt for the Python backend. Do not introduce pnpm or yarn.
- Avoid mass formatting, renaming, or dependency upgrades unrelated to the task.
- If a Jira issue ID is supplied, reference it in the implementation summary and relevant documentation.
Verification and Definition of Done
- Run applicable lint, formatting checks, TypeScript checks, tests, and builds using scripts available in the repository.
- For backend changes, run relevant unit/integration tests; for migrations, verify the migration in a safe development environment.
- For UI changes, verify responsive behavior, theme variants, keyboard navigation, and key loading/error states when tooling allows.
- For infrastructure changes, validate Docker Compose configuration and document required environment variables.
- Do not claim the application works on the VPS unless deployment and its public/server URL have actually been checked.
- If commands cannot run, explicitly report what was not verified and why. Never fabricate test results.
- Follow DEFINITION_OF_DONE.md when present; do not silently weaken its requirements.
Communication and completion report
- Communicate with the team in Polish unless the task specifies another language. Keep code identifiers, API names, and technical documentation in English unless existing conventions differ.
- At the end of each task, summarize: what changed, key files, checks performed and their results, and remaining risks or follow-ups.
- State assumptions when requirements are ambiguous; ask a focused question before making an irreversible or high-impact choice.
Implementation order
Prefer incremental delivery: foundation and layouts → authentication/RBAC → document management → OCR queue/worker → approval workflow → integrations, audit and deployment hardening. This is a guideline, not permission to implement features outside the requested scope.
