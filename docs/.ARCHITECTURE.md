# Fluxis EOD: Technology Stack & Architecture Specification

> This document is aligned with `docs/.AGENTS.md`. If the two ever disagree, `docs/.AGENTS.md` is authoritative for the technology stack and working rules; update this file accordingly.

## 1. Project Overview

**Project:** Fluxis  
**Type:** Electronic Document Management System (EOD)  
**Architecture:** Modular Monolith, REST API (OpenAPI), SPA, separate background OCR worker  
**Deployment:** Docker Compose on a small Linux VPS, behind a reverse proxy  
**Languages:** TypeScript (frontend), Python (backend)

Fluxis is a web-based document management system designed for uploading, organizing, reviewing, approving, and archiving documents.

The application should support role-based access control (RBAC), document workflows, OCR processing, user administration, audit logs, and integration with external identity providers such as Active Directory through LDAPS.

The architecture should prioritize maintainability, modularity, security, and efficient resource utilization.

Do not add a second UI framework, a new backend framework, microservices, Kubernetes, or cloud-managed dependencies without explicit approval.

```text
│   ├── utils/             # shared helpers (e.g. file handling)

├── requirements.txt
└── run.py
```

Business modules (auth, users, roles, documents, workflow, ocr, integrations, audit, notifications) are split across these layers rather than into separate packages:

- `routes/` parse the request, call a service, and map results to HTTP responses. No business logic or direct queries.
- `services/` implement use cases, enforce permissions and document access, and write audit entries.
- `models/` handle persistence only.
- `schemas/` validate incoming DTOs and shape outgoing responses.

Use consistent API error responses and appropriate HTTP status codes. Keep the OpenAPI specification in sync with changed endpoints and with frontend types.

Avoid introducing microservices or unnecessary distributed architecture.

## 5. Database

Use SQLAlchemy with Flask-Migrate. SQLite is the default (`DATABASE_URI`); keep models and queries portable so that the database can later be switched (e.g. to PostgreSQL) through configuration and a reviewed migration, without code redesign.

Initial entities:

- User
- Role
- Permission
- UserRole
- RolePermission
- Document
- DocumentVersion
- DocumentStatus
- DocumentType
- DocumentWorkflow
- WorkflowStep
- ApprovalDecision
- OcrJob
- AuditLog
- IntegrationConfiguration

Use UUID identifiers where appropriate.

Store document metadata in the database. Store uploaded files in a dedicated private storage volume (`UPLOAD_FOLDER`), never as binary blobs in database records and never in a publicly served directory.

Implement appropriate foreign keys, indexes, uniqueness constraints, timestamps and referential integrity.

All schema changes go through reviewed Flask-Migrate migrations. Never reset or drop a database, erase data, or apply destructive migrations without explicit approval.

## 6. OCR and Background Jobs

OCR is performed with Google Gemini (`google-genai`) and must be asynchronous. HTTP request handlers must never call Gemini synchronously; they only create a job and return.

Workflow:

1. User uploads a document.
2. Backend validates the file (size, allowed format, actual content type, safe storage path) and permissions.
3. Document metadata is stored in the database.
4. File is saved in private storage.
5. An `OcrJob` record is created with status `pending`.
6. A separate background OCR worker process picks up pending jobs and calls Gemini.
7. Extracted text/data and the final status are saved on the job.
8. Frontend polls the OCR status through the REST API.

Job states:

- Pending
- Processing
- Completed
- Failed

Requirements:
- Bounded retries (tenacity) with backoff, a per-job execution timeout, and a clear error message on failure.
- Idempotent, retry-safe processing: a job must be claimed atomically so that it is not processed twice.
- Limited worker concurrency appropriate for a small VPS.
- File size limits (currently `MAX_CONTENT_LENGTH` = 16 MB).
- Treat OCR/Gemini output as untrusted input (validate and sanitize before storing or rendering). Never log document content or the API key.

Initially support PDF, PNG and JPEG.

The worker runs from the same backend codebase and image, as its own Docker Compose service. The default queue is the `OcrJob` table itself (no additional infrastructure). Introducing a dedicated broker (e.g. Redis with RQ/Celery) requires explicit approval.

> **Current state:** `OcrService.start_ocr` still calls Gemini synchronously inside the request and no worker exists yet. Moving this to the background worker is part of the OCR phase.

## 7. Authentication and Authorization

Use secure session-based (or token-based) authentication.

Requirements:

- Password hashing using Argon2id (argon2-cffi)
- Secure authentication endpoints with rate limiting against brute force
- Role-based access control (see `docs/RBAC_Permissions_Matrix.md`)
- Backend permission and document access checks for every relevant operation
- Protected frontend routes (UX only)
- Session expiration handling
- Audit logging for security-relevant actions, without credentials, tokens or document content
- Optional future LDAPS integration

Prefer HttpOnly, Secure, SameSite cookies. Do not store sensitive authentication tokens in localStorage or sessionStorage. Protect cookie-based state-changing endpoints against CSRF.

The frontend must not be considered an authorization boundary.

## 8. Infrastructure and Deployment

Target environment: small Linux VPS, Docker Compose, behind a reverse proxy.

Repository layout:

```text
fluxis/
├── frontend/
├── backend/
├── infrastructure/
│   ├── docker/            # Dockerfiles (frontend, backend)
│   ├── nginx/             # reverse proxy / static file configuration
│   └── scripts/
├── compose.yaml
├── backend/.env.example
├── README.md
└── DEFINITION_OF_DONE.md
```

Container services:

- Frontend + reverse proxy (nginx serving the built SPA and proxying `/api` to the backend)
- Backend (Flask on Gunicorn)
- OCR worker (same backend image, worker entry point) — planned

Only the nginx HTTP/HTTPS port is published. The backend, the worker and the database are reachable only on the internal Docker network. With SQLite, the database file lives on a persistent volume shared only by the backend and the worker.

Use persistent volumes for the database and document storage.

Provide health checks, restart policies, environment-based configuration (`backend/.env`, with placeholders maintained in `.env.example`), resource limits, and a documented backup/restore procedure for the database file and the storage volume.

Never commit `.env`, private keys, credentials, real user data or production documents.

Do not claim the application works on the VPS unless deployment and its public URL have actually been checked.
